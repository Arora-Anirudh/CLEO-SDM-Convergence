# Work log: 2026-07-28

This is the detailed learning record for the first day of work in the permanent
research repository. It records what was changed, why it was changed, what was
run, what was learned, and what remains unproven. It is written for later
study—not as a claim that the final convergence experiment has already been
defined.

## 1. Why a new repository was created

The initial CLEO onboarding was done inside a personal clone of the upstream
CLEO repository. Clara recommended a separate research repository that *calls*
CLEO as an external dependency, following the architecture of
`PerformanceTestingCLEO`. This gives the project:

- an independent, public and citable history owned by Anirudh;
- a clean boundary between upstream CLEO and experiment-specific code;
- a place for later 0-D, 1-D and 2-D configurations;
- reproducible configuration, Slurm, analysis and provenance files;
- no risk of accidentally pushing research changes into upstream CLEO.

The resulting public repository is `Arora-Anirudh/CLEO-SDM-Convergence`, under
the BSD-3-Clause license.

## 2. Repository architecture

The main layers are:

| Layer | Important path | Responsibility |
| --- | --- | --- |
| Scientific configuration | `config/collisions0d_reference.yaml` | Initial DSD parameters, box size, `N_SD`, timesteps and output settings |
| External model | `src/extern/cleo/CMakeLists.txt` | Fetch the canonical CLEO URL at one exact commit |
| Applications | `src/collisions0d/` | Choose Golovin or Long collision-coalescence and assemble a null-dynamics box |
| Initialization | `scripts/prepare_collisions0d_inputs.py` | Generate deterministic binary grid and SD inputs from a recorded seed |
| Runtime materialization | `scripts/materialize_collisions0d_config.py` | Convert portable YAML paths into absolute, run-specific Levante paths |
| Levante workflow | `scripts/levante/` | Build, run, validate and analyze without overwriting prior products |
| Diagnostics | `scripts/analyze_collisions0d.py` | Read CLEO output with CLEO tools and calculate distribution/bulk metrics |
| Compact records | `results/` | Version small figures, tables, metadata and checksums; raw Zarr stays on SCRATCH |

The pinned upstream version is:

```text
repository: https://github.com/yoctoyotta1024/CLEO.git
commit:     83318c23223546d10759d202d70f4fa2f7fe4688
```

A commit pin is important because a floating `main` branch can change. The same
research commit must continue to build against the same CLEO source.

## 3. What the `collisions0d` code constructs

`main_impl.hpp` creates:

1. one Cartesian gridbox from the binary grid file;
2. superdroplets from the binary initialization file;
3. null dynamics;
4. null movement and null boundary conditions;
5. exactly one collision-coalescence microphysical process;
6. observers for time, radius, multiplicity, solute mass and SD ID;
7. a filesystem-backed Zarr dataset.

The Golovin and Long source files differ only in the pair-probability kernel
they pass into the shared collision/coalescence machinery.

“0-D” means that no spatial transport or dynamical evolution is solved. The
initializer still gives coordinates to match Clara's reference
`collisions0d`, but those coordinates do not move.

## 8. Why two random seeds are required

The initialization seed controls the sampled time-zero SD population. Until
today, CLEO's collision RNG pool was initialized from `std::random_device`.
Therefore the first run had reproducible initialization but no deliberately
replayable collision stream.

The new design separates:

```text
INITIALIZATION_SEED -> which SD population exists at t = 0
COLLISION_SEED      -> how that fixed population is shuffled and sampled later
```

This does not remove stochasticity. It makes the stochastic experiment
controlled and auditable.

## 9. Collision-seed implementation

The project now stores a minimal patch against the exact CLEO pin. The patch
adds one constructor that initializes CLEO's existing Kokkos RNG pool from a
provided unsigned 64-bit seed. All collision equations, kernel probabilities,
shuffle code and draw locations remain CLEO code and remain unchanged.

The change is applied only to CMake's fetched source in the local build tree.
The online upstream CLEO repository is not edited.

Project-owned code now:

- parses and validates the seed;
- prints it at model startup;
- passes it into both Golovin and Long collision-coalescence;
- requires it in the Levante runner;
- records it in every run manifest.

The exact rationale and limitations are in ADR 0002.

## 10. Replay validation designed today

The dedicated validation job will run three one-thread Golovin cases:

| Case | Initialization | Collision stream | Expected result |
| --- | --- | --- | --- |
| A | seed 12345 | seed 67890 | reference |
| B | seed 12345 | seed 67890 | byte-identical to A |
| C | seed 12345 | seed 98765 | different from A |

It checks that all three initialization binaries have the same SHA-256 and then
compares the complete Zarr file trees. Passing this gate proves exact replay in
the tested one-thread execution mode. It does not yet prove multi-thread byte
replay.

## 13. First seeded-build attempt: safely stopped

Build job `26517977` requested one node, one task, eight CPU cores, 8 GiB and
30 minutes on `bb1153/shared`. Levante's memory/core policy recorded nine
requested and ten allocated CPUs. The job started and stopped after seven
seconds, before compilation or model execution.

The first patch file used zero-context unified-diff hunks. A local
`git apply --check` accepted the file, but standard `git apply` requires
additional handling for zero-context patches and placed the additions at the
end of the fetched header. The repository's post-application
`git diff --check` detected the malformed result and failed CMake. This was the
intended safety behavior: no executable containing the malformed header was
built.

The correction is:

- use anchored, ordinary unified-diff hunks;
- leave CLEO's existing blank line in place rather than add one;
- verify that the seeded constructor occurs before the header guard closes;
- restore only the failed job's one modified build-local fetched header before
  reconfiguration.

This failure changed no online CLEO source, version-controlled research data,
prior executable, or prior Zarr output.

## 15. Golovin convergence protocol and Stage-0 implementation

After the onboarding/example work, the researcher chose to complete the
Golovin convergence calibration before beginning a Long convergence study.
The permanent-repository protocol was written first so the numerical and
statistical definitions did not emerge after seeing production results.

The Stage-0 implementation then added:

- one fixed logarithmic-radius grid for formal distribution comparison;
- a no-smoothing mass-density histogram and relative L1 metric;
- explicit mass-underflow and mass-overflow fractions;
- exact untruncated Golovin radius moments \(M_0,M_3,M_6\) and signed errors;
- mass conservation, 40 μm onset fraction, provisional larger-drop fraction
  and mass-weighted q99;
- interval-censored `t10` with lower/upper output bounds;
- per-member time and member-level summary tables;
- Student-\(t\) and deterministic bootstrap ensemble summaries;
- a deterministic metadata-only development matrix with separate 32-bit
  initialization and 64-bit collision seeds;
- explicit per-case \(N_\mathrm{SD}\), collision timestep, output interval and
  end-time materialization;
- a one-row-per-array-task Levante wrapper;
- completed-only resume semantics and strict incomplete-path refusal;
- running, failed and complete manifest states;
- project/build commit matching, tracked-clean checks, environment fields and
  file/Zarr SHA-256 provenance.

The official CLEO smoothed validation figure remains available. It is now
explicitly separated from the fixed-bin formal convergence metric because its
bandwidth changes with \(N_\mathrm{SD}\).

Local validation used the existing locked Python environment from the main
